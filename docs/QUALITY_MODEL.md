# Test Suite Quality Model

A test is valuable when it provides distinct, trustworthy evidence about behavior that matters. Quality cannot be reduced to count or line coverage.

## Oracle authority
Identify what defines correct behavior: requirement/business invariant, public contract, reference implementation, accepted current behavior, characterization observation, generated expectation, or implementation-derived expectation.

Implementation-derived expectations are weak when the implementation is disputed.

## Assertion strength
Ask whether the test would fail for a materially incorrect outcome.

Weak patterns include no assertion, status-only when business effects matter, existence-only when invariant/state matters, giant snapshots with no semantic focus, and expected values generated by the same faulty logic.

## Path/risk coverage
Consider happy, invalid, boundary, degraded, retry/idempotency, recovery/reversal, concurrency, authorization, migration, partial failure, and resource/timing behavior when relevant.

## Fidelity
Classify honestly: pure/unit, component, mocked integration, real integration, contract, E2E, simulator/emulator, target/production-like.

Mocks must not be reported as real integration.

## Independence
Watch for shared wrong assumptions: same agent generated implementation and tests, same helper computes expected and actual, fixture mirrors implementation, or multiple generated artifacts derive from one incorrect source.

## Maintainability
Smells include duplicate setup/cases, oversized fixtures, order dependence, sleeps, excessive mocking, implementation-detail assertions, giant snapshots, unclear failure messages and hidden shared state. A smell is a hypothesis, not an automatic defect.

## Distinct evidence contribution
Two tests can execute different files while proving the same thing. A slower duplicate may add little evidence. Similar tests can still be justified by distinct risk, fidelity, platform, contract, or regression history.

## Decorative-green signals
- high coverage with weak assertions;
- only happy paths;
- claimed boundary mocked away;
- no observable effect verification;
- always-retried flake;
- expected behavior copied from implementation;
- critical E2E-only rule with no useful isolating evidence;
- meaningful mutation survivor;
- tests removed during refactor without equivalent risk coverage.

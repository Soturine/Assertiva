# Test Suite Quality Model

A test is valuable when it provides distinct, trustworthy evidence about behavior that matters. Quality cannot be reduced to count or line coverage.

## Oracle authority
Identify what defines correct behavior: requirement/business invariant, public contract, reference implementation, accepted current behavior, characterization observation, generated expectation, or implementation-derived expectation.

Implementation-derived expectations are weak when the implementation is disputed.

## Assertion strength
Ask whether the test would fail for a materially incorrect outcome.

Weak patterns include no assertion, status-only when business effects matter, existence-only when invariant/state matters, accepting any exception when the error contract is specific, giant snapshots with no semantic focus, and expected values generated by the same faulty logic.

Expected-error assertions are valid positive evidence when the product contract requires rejection. Their strength depends on how specifically they prove the relevant failure contract and state effects.

## Path/risk coverage
Consider happy, invalid, boundary, degraded, retry/idempotency, recovery/reversal, concurrency, authorization, migration, partial failure, startup/configuration, and resource/timing behavior when relevant.

## Fidelity
Classify honestly: pure/unit, component, mocked integration, real integration, contract, E2E, simulator/emulator, target/production-like.

Mocks must not be reported as real integration.

## Independence
Watch for shared wrong assumptions: same agent generated implementation and tests, same helper computes expected and actual, fixture mirrors implementation, shared inherited/composed test declarations reuse one wrong oracle across many materializations, or multiple generated artifacts derive from one incorrect source.

## Maintainability
Smells include duplicate setup/cases, oversized fixtures, order dependence, sleeps, excessive mocking, implementation-detail assertions, giant snapshots, unclear failure messages and hidden shared state. A smell is a hypothesis, not an automatic defect.

## Distinct evidence contribution
Two tests can execute different files while proving the same thing. A slower duplicate may add little evidence. Similar tests can still be justified by distinct risk, fidelity, platform, contract, implementation type or regression history.

Many materialized tests from one shared declaration are not automatically duplicates; preserve declaration/materialization provenance before judging distinct contribution.

## Decorative-green signals
- high coverage with weak assertions;
- only happy paths;
- negative tests that accept any exception;
- error-status-only checks while structured/state behavior matters;
- claimed boundary mocked away;
- no observable effect verification;
- rejection asserted without rollback/no-side-effect evidence where required;
- always-retried flake;
- expected behavior copied from implementation;
- critical E2E-only rule with no useful isolating evidence;
- meaningful mutation survivor;
- tests removed during refactor without equivalent risk coverage.

## Parameterization and materialization quality

Parameterized/table-driven tests should preserve individual invocation identity when the runner exposes it. Audit whether material boundaries and invalid classes are represented, whether a failed row is replayable, and whether the parameter source is independent from the implementation under test.

Inherited/composed/shared tests should preserve declaration and materialization identity. Overrides, lifecycle hooks, generic fixture arguments and shared oracle concentration affect the meaning of the executed suite.

## Structured failure behavior

Validation and error handling are behavior. Prefer stable structured semantics such as error type/code/path/location/context/status over incidental message-only equality unless wording itself is required. Also verify state effects, rollback/compensation, recovery and sensitive-data behavior when those are part of the contract.

Expected rejection is a successful product behavior when rejection is the contract. Do not confuse expected product error with test failure.

## Generative evidence

Property, fuzz and metamorphic tests complement examples when input space is large. Preserve seeds, counterexamples, shrinking/minimization and corpora so failures remain reproducible.

## Coverage quality

Statement/line, branch/decision, condition, function/method, instruction and test-specific coverage answer different questions. None proves oracle adequacy by itself. Executing error/exception branches does not prove their contracts or state effects were asserted.

## Refactor safety

A suite should be judged partly by whether it can detect unintended behavioral drift during refactoring. High coverage with weak oracles is not a safety net. For consequential refactors, map important behaviors/contracts to credible detectors and challenge the suite with negative controls or mutation where proportionate.
